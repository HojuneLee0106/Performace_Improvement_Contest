# Performance_Improvement_Contest
# 카카오 약관 QA 결과기 (KTB 4기 AI 성능 개선 대회 · 13팀)

카카오 약관 4종에서 질문에 해당하는 조항을 찾아 **답변과 근거 조항을 함께 반환**하는 RAG 시스템입니다.
Google Colab T4 한 대, 외부 API 없이 동작합니다.

```
                        예선 채점 87.138 / 100
  ┌─────────────────────┬─────────────────────┬──────────────────────┐
  │  검색 MRR  1.0000   │  키팩트 F1  0.6638  │  LLM 판정   94.450   │
  │      20.0 / 20      │     19.913 / 30     │     47.225 / 50      │
  └─────────────────────┴─────────────────────┴──────────────────────┘
   공개 10문항 검색 recall 12/12 · precision 12/12 · 전 문항 1위
```

## 파이프라인

```
질문
 │
 ├─▶ ① 약관명 감지 ────────────────────┐
 │     "카카오 통합 약관과 세부지침이…"  │  질문에 약관명이 있으면
 │                                      │  그 문서로 검색 범위 제한
 ▼                                      ▼
② BM25 검색 (문자 bigram · 조 제목 3배 가중)
 │     72개 조항 × 4개 약관
 ▼
③ 근거 선별   1위 점수 대비 0.75 이상만 채택 (최대 4개)
 │     P01 ★1.00 0.43 0.28  → 1개
 │     P02 ★1.00 ★1.00 ★0.93 → 3개 (문서 간 중복 조항)
 ▼
④ 컨텍스트 구성   조 본문에 [제12조 제①항] 라벨 삽입
 │     검색 단위는 조, 근거 제시 단위는 항
 ▼
⑤ 생성   Qwen2.5-7B-Instruct (4bit nf4) · greedy · 단일 패스
 │
 ▼
{"answer": "...", "retrieved": [["카카오 위치정보 이용약관", 12]]}
```

**기술 선택과 이유**

| 단계 | 선택 | 왜 |
|---|---|---|
| 원문 배포 | 조 단위 JSON을 gzip+base64로 셀에 임베드 (~43KB) | Drive 마운트·사전 업로드 금지 + 런타임 다운로드는 페이지 장애 시 전량 실패 |
| 토크나이저 | 한글 문자 bigram | Kiwi가 MRR 1.000으로 더 높았지만 의존성 0을 택함 (아래 참고) |
| 청킹 | 조(條) 단위 고정 | 채점 단위가 `[문서명, 조번호]` — 검색 단위와 일치시킴 |
| 근거 선별 | 상대 비율 임계값 (τ=0.75) | 중복 조항이 있는 문항만 자연스럽게 여러 개가 살아남음 |
| 생성 | 7B 4bit · greedy | T4 16GB·fp16 제약 안에서 지시 이행력 확보. `do_sample=False`로 재현성 |

## 이 프로젝트에서 가장 크게 배운 것

### 결론이 반대로 나오는 실패는 프롬프트가 아니라 데이터를 의심한다

두 문항(P08·P09)이 정답과 **정반대** 결론을 냈습니다. 프롬프트를 여섯 번 고쳤지만 잡히지 않았고,
원인은 전부 PDF 파싱 단계에 있었습니다.

```
버그 ①  법률 상호참조를 조 헤더로 오인
        "위치정보법 제26조2항" → 제12조가 96자에서 잘림
        수정: 줄 맨 앞에서 시작하는 헤더만 인정

버그 ②  3단 컬럼 목차가 본문을 밀어냄
        목차 조각(193자)이 실제 제3조 본문(182자)을 이김 → 검색 순위 72위 중 72위
        수정: 길이 대신 "남의 조 헤더를 몇 개 무는가"로 판정

버그 ③  pdftotext -raw 의 공백 소실
        통합 약관 4·8·10·11조 공백 증발 ("시한게시물")
        수정: 통합 약관만 -layout 으로 추출

버그 ④  -layout 의 2차 부작용
        따옴표가 자리 밖으로 밀림:  등(이하 세부지침 ) ' ' 의
        수정: 고아 따옴표 제거 + (이하 X) 재감싸기
```

추출기 선택은 문서마다 달라야 했습니다. `-raw`/`-layout` 중 하나가 전역 정답이 아니었습니다.
코퍼스를 고치자 P09가 **한 번에** 정상화됐습니다.

색인 전에 검증 6종(조번호 연속·개수, 헤더 일치, 본문 유실·겹침, 헤더 혼입, 카나리 문장)을 실행해
같은 실수가 조용히 지나가지 않도록 했습니다.

### 검색 단위(조)와 근거 제시 단위(항)를 분리한다

평균 378토큰짜리 조항을 통째로 넣으니, **컨텍스트 안에 정답 문장이 있는데도** 모델이 못 집는
실패가 반복됐습니다(①항 결론절이 뒤이은 1·2·3호 열거에 묻히는 식).

청킹을 바꾸는 대신 **프롬프트 컨텍스트를 만드는 순간에만** 항 경계를 드러냈습니다.
코퍼스·색인·`retrieved` 반환은 조 단위 그대로입니다.

```
before                          after
─────────────────────           ─────────────────────
제 12 조 (8세 이하의…)          제 12 조 (8세 이하의…)
① 회사는 아래의 …               [제12조 제①항]
1. 8세 이하의 아동              ① 회사는 아래의 …
2. 피성년후견인                 1. 8세 이하의 아동
…                               2. 피성년후견인
③ 보호의무자는 …                …
                                [제12조 제③항]
                                ③ 보호의무자는 …
```

항 표기가 문서마다 다릅니다 — 통합 약관은 숫자가 항, 나머지 3종은 ①이 항·숫자가 호.
항 표기가 없는 조는 라벨 없이 유지합니다(없는 구조를 지어내지 않기 위해).
전 72조항 본문 손실 0을 확인했습니다.

부수 효과로 모델이 시키지 않아도 조항 번호를 인용하기 시작했습니다 — `"제10조 제2항에 따르면 …"`.

### 중간 지표가 올라도 최종 점수는 내려갈 수 있다

"모델이 근거 문장을 고르고 → LLM이 다듬는" 2단계 구성을 시도했다가 **폐기**했습니다.

```
                    단일 패스      2단계
키팩트 재현율        74.7%    →   78.6%   ▲ +3.9%p
LLM 판정             94.45    →   93.15   ▼ −1.30
p50 지연             8.19s    →  11.44s   ▼ +40%

P08  86.5 → 70   트랩 문항 결론 뒤집힘
P03   100 → 94   「(추가 항목 없음)」을 지어냄
P07   100 → 94   고유명사 유실
```

재작성 단계가 원문에 없는 내용을 만들어냈습니다.
키팩트 재현율만 보고 채택했다면 점수를 잃었을 변경입니다.
이후 모든 개선은 중간 지표와 최종 지표를 함께 확인한 뒤에만 채택했습니다.

### 언어·형식 제약은 프롬프트보다 디코딩 단에서

프롬프트 규칙이 7개까지 늘어나자 가장 긴 조항에서 **중국어가 출력**됐습니다.
`"한국어로만"`을 프롬프트 맨 앞으로 옮겨도 재발했습니다.

```python
# 지시 대신 디코딩 후보에서 제거한다.
# 약관 원문에 CJK 통합한자가 없음을 사전 확인 (㈜는 이 영역이 아님)
CJK_BAN = [[tid] for tid in range(len(TOKENIZER))
           if any("\u4e00" <= ch <= "\u9fff" for ch in TOKENIZER.decode([tid]))]

MODEL.generate(..., bad_words_ids=CJK_BAN)
```

**텍스트 유사도만으로는 문서를 구분할 수 없습니다.**

대응: 질문에 약관명이 명시되면 하드 필터, 없으면 중복 조항을 함께 신고.

제목이 같은 「약관 외 준칙」이지만 충돌 규칙 자체가 없는 조항이라,

## 품질과 속도

```
                        p50      p95     rps      예산 120초 대비
3B fp16 (1차)          6.31s    9.10s   0.286        8%
3B fp16 (파서 수정 후)  6.11s    7.12s   0.314        6%
7B bnb-4bit nf4        9.54s   21.13s   0.170       18%   ← 채택

성공률 1.000 · 타임아웃 0건 · 문서명 위반 0건
```

속도는 **의도적으로 내줬습니다.** 대회 요강상 HTTP 지표 자체에는 배점이 없고 예선 통과는
품질로만 결정되므로, 예산의 18%만 쓰고 나머지를 품질에 투자하는 편이 유리하다고 판단했습니다.

T4에서 bnb nf4는 AWQ보다 디코딩이 느립니다. 두 구성의 답변 품질은 동등했으므로,
**AWQ로 되돌리면 품질을 깎지 않고 속도만 회수할 수 있습니다.**

## 평가기 (`evaluator_13.ipynb`)

문항 세트 + 답변 파일을 받아 0~100 점수를 산출합니다. 문항 수를 하드코딩하지 않고
입력 JSON 길이를 읽으므로 10문항·30문항에 같은 코드가 그대로 돌아갑니다.

```
총점 100 = MRR 15  +  근거 정밀도 15  +  키팩트 F1 30  +  Gemini 판정 40

Gemini 판정 4축   accuracy 0.40 · grounding 0.25 · completeness 0.20 · clarity 0.15
```

**설계에서 신경 쓴 것**

- **MRR만으로는 부족합니다.** MRR은 정답이 처음 나온 순위만 보므로 뒤에 오답을 아무리 채워도
  값이 같습니다. `evidence_precision` 축을 따로 두어 "필요한 만큼만 냈는가"를 반대편에서 측정합니다.
- **판정 프롬프트에 약관 원문을 넣지 않습니다.** 정답 핵심 내용이 곧 채점 기준이므로 그것으로
  충분하고, 입력 토큰이 줄어 API 비용도 아낍니다.
- **키팩트 F1은 2글자 이상 내용 토큰 집합 기반.** 조사·어미를 떼는 쪽이 오히려 오차가 컸습니다
  (실제 답변·채점 결과로 규칙 조합을 비교해 선택).
- **API 키를 코드에 넣지 않습니다.** 환경변수 → Colab 보안 비밀 → `getpass` 순으로 탐색.
- **제출 전 self-check 내장.** 최상위 키·후보 수·ID 중복·금지 키·점수 범위·status를 검사합니다.
  한 문항이라도 실패하면 파일 전체가 순위에서 빠지므로 `MAX_RETRY=4`로 넉넉히 재시도합니다.

## 안전장치

채점 파이프라인이 한 문항의 실패를 **문항 전체 폐기**로 처리하기 때문에, 반환 직전에 방어를 넣었습니다.

```python
# 생성이 죽어도 검색 점수는 건진다
try:
    answer = generate(...)
except Exception as exc:
```
